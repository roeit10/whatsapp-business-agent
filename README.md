# סוכן AI בוואטסאפ לעסק

בוט שקורא הודעות מהוואטסאפ של בעל העסק, מבין מה שאלו אותו, **ניגש לנתונים האמיתיים של העסק** ועונה ללקוח במקומו.

זה ההבדל מצ'אטבוט שמאומן על קובץ: הוא לא "זוכר" את המלאי, הוא **הולך ובודק** בכל שאלה. שיניתם מחיר בגיליון לפני שנייה — התשובה הבאה כבר לפי המחיר החדש.

הדוגמה בריפו היא חנות חיות. מחליפים את הנתונים ומקבלים כל עסק אחר.

```
לקוח בוואטסאפ  ──>  Green API  ──>  השרת שלך  ──>  המודל בוחר באיזה כלי להשתמש
                                        │
                                        ├── מאגר ידע     (Google Docs)
                                        ├── מלאי         (Google Sheets)
                                        ├── הזמנות       (Google Sheets)
                                        │
                                        └── אתר קטלוג    (נבנה מאותם נתונים)
                                        │
לקוח בוואטסאפ  <──  Green API  <────────┘
```

| "אני צריך אוכל לכלב" | לא שופך רשימה — שואל שאלת סינון אחת ואז ממליץ |
| "יש אקאנה לגורים?" (אזל) | אומר שאזל **ומציע חלופה זמינה שמתאימה לאותה חיה** |
| "יש אוכל לסוסים?" | לא מוצא, ואומר שהוא **לא מופיע אצלנו** — לא שהוא אזל |
| "מתי מגיע אליי המשלוח?" | מזהה את הלקוח לפי מספר הוואטסאפ ושולף את ההזמנה |

| "יש לכם משלוח לאילת?" (לא כתוב בשום מקום) | **שואל אתכם בקבוצת וואטסאפ פנימית**, שולח ללקוח את מה שעניתם, ושומר את התשובה לפעם הבאה |

## התחלה מהירה

**1. צרו ריפו משלכם** — לחצו **`Use this template`** למעלה. אל תעבדו בתוך הריפו הזה: Railway לא יכול לפרוס מריפו שאינכם הבעלים שלו, וכל commit ינסה להידחף לחומר הלימוד.

**2. פתחו את התיקייה ב-Claude Code ואמרו:** "בוא נתחיל".

זהו. הריפו כולל תהליך אונבורדינג מונחה — קלוד יריץ בדיקה, יראה מה חסר, וילווה אתכם שלב אחרי שלב: יתקין את הכלים, ינחה אתכם איפה להתחבר, יבקש את המפתחות, ויתחיל לבנות רק כשהכול מחובר.

לבדיקה ידנית בכל שלב:

```bash
npm run doctor
```

הבדיקה מדווחת מה מחובר, מה חסר, ובאיזה שלב להתחיל.

## הנתונים

שלושה קבצים בגוגל, כולם משותפים ב־**"כל מי שיש לו את הקישור — צפייה"**:

| קובץ | מבנה |
|---|---|
| **מסמך ידע** (Docs) | טקסט חופשי: שעות, משלוחים, החזרות, מדיניות, מחירי שירותים |
| **גיליון מלאי** (Sheets) | `מקט · שם המוצר · מותג · קטגוריה · מתאים ל · גודל · מחיר · כמות במלאי · ימי אספקה` |
| **גיליון הזמנות** (Sheets) | `מספר הזמנה · שם לקוח · טלפון · תאריך הזמנה · פריטים · סטטוס · תאריך משלוח צפוי · מספר מעקב` |

**עמודת הטלפון בהזמנות מזהה את הלקוח.** פורמט לא משנה: `0501234567` ו-`972501234567` נחשבים זהים.

**`מתאים ל`** קובעת איזו חלופה תוצע כשמוצר אזל — לפי החיה ושלב החיים, לא לפי המותג.

**`ימי אספקה`** היא כמה זמן אריזה מחזיקה. יחד עם תאריך ההזמנה, זה מה שמאפשר לסוכן להציע חידוש.

> **למה לא צריך שום הרשאה?** לקובץ גוגל משותף יש נתיב ייצוא ציבורי: `docs.google.com/document/d/<ID>/export?format=txt` ו-`.../spreadsheets/d/<ID>/export?format=csv`. שניהם מחזירים את התוכן ב-`curl` נקי בלי טוקן. שימו לב שה-API הרשמי (`sheets.googleapis.com`) מחזיר 401 גם לקובץ ציבורי — נתיב ה-`export` הוא היחיד שעובד בלי הזדהות, והוא לקריאה בלבד.

לייצור נתוני דוגמה: `python3 scripts/gen-demo-data.py` מייצר 150 מוצרים ב-13 קטגוריות ו-40 הזמנות של 12 לקוחות על פני חצי שנה, כולל לקוחות חוזרים.

## התאמה לעסק אחר

שלושה דברים משנים, הקוד נשאר:

1. **הנתונים** — הקבצים שלכם במקום של חנות החיות
2. **פרטי העסק** — שם, טלפון, למי מפנים. הכל ב-`.env`
3. **התחום והטון** — מה מותר לו לענות עליו, ואיך

| עסק | "מלאי" הופך ל | "הזמנות" הופך ל |

**כתבו בתיאור הכלי מתי לקרוא לו, לא רק מה הוא עושה.** זה מה שגורם למודל להשתמש בו במקום לנחש.

## שאלה שאין עליה תשובה — הסוכן שואל אתכם

כשהסוכן מחפש בכלים ולא מוצא, הוא לא מנחש ולא סוגר את הלקוח ב"אין". הוא מעביר את השאלה לקבוצת וואטסאפ פנימית, ומה שתענו שם חוזר ללקוח ונשמר לפעם הבאה.

יצירת הקבוצה (פעם אחת):

```bash
npm run create-group -- 972501234567
```

המספר הוא הטלפון שלכם בפורמט בינלאומי. הסקריפט יוצר את הקבוצה, שולח בה הודעת הסבר ומדפיס את השורה שצריך להוסיף ל-`.env` וגם למשתני הסביבה ב-Railway:

```
OWNER_GROUP_CHAT_ID=1203630...@g.us
```

איך זה נראה בפועל:

1. לקוח שואל "יש לכם משלוח לאילת?" — לא כתוב בשום מקום.
2. בקבוצה מופיעה השאלה עם שם הלקוח, מה שהוא כתב, ומספר סידורי (`#7`).
3. ללקוח יוצא "בודק את זה ואחזור אליך".
4. אתם עונים בקבוצה: "רק עד באר שבע, לאילת לא".
5. הלקוח מקבל הודעה מנוסחת, ובקבוצה מופיע אישור: מה נשלח ומה נשמר במאגר.
6. הלקוח הבא ששואל את אותה שאלה מקבל תשובה מיד, בלי שתדעו על זה.

פרטים שכדאי להכיר:

- **כמה שאלות פתוחות בו זמנית** — השיבו על הודעת השאלה עצמה, או פתחו את התשובה ב-`#7`. עם שאלה פתוחה אחת אפשר פשוט לענות.
- **הודעה שאינה תשובה** ("רגע, בודק") לא נשלחת לשום מקום. אפשר לדבר בקבוצה בחופשיות.
- **מה שנשמר** הוא עובדה על העסק, לא התשובה ללקוח. הנחה חד־פעמית או מקרה חריג לא נכנסים למאגר — תראו את זה בהודעת האישור בקבוצה.
- **מאגר הידע הנלמד** יושב כברירת מחדל ב-`data/learned.json` ונספח לדוק בגוגל, לא דורס אותו. הדוק נקרא בלי הזדהות ולכן הוא קריאה בלבד.
- **מאגר הידע שלכם לא חייב להיות Google Docs.** אם המידע יושב ב-Notion, ב-Airtable, ב-CRM או בבסיס נתונים — ואפשר לכתוב אליו — עדיף שהתשובות ייכנסו לשם ולא לקובץ בצד. כל ההחלפה היא שתי פונקציות ב-`src/knowledge.js`: `addFact` שומר עובדה, `knowledgeAddendum` מחזיר את מה שנספח לתשובת הכלי. תגידו לקלוד איפה המאגר שלכם והוא יחבר.
- **בלי `OWNER_GROUP_CHAT_ID`** הסוכן פשוט מפנה את הלקוח לטלפון שלכם, כמו קודם.
- הקובץ יושב ב-`data/`, אז ה-Volume ב-Railway הוא מה שמשמר את מה שנלמד בין deploys.

## החלטות שכדאי להבין לפני שמשנים

**הטלפון של הלקוח לא עובר דרך המודל.** ב-`buildExecutors` מספר השולח נסגר בתוך הפונקציה ומגיע מה-webhook. אם הוא היה פרמטר של כלי, אפשר היה לשכנע את המודל בשיחה למשוך הזמנה של לקוח אחר.

**כמות המלאי לא מגיעה למודל בכלל.** `publicProduct` מסירה את העמודה ומחליפה ב"במלאי"/"אזל". אפשר היה לכתוב בפרומפט "אל תגיד כמה נשאר", אבל לקוח ששואל ישירות הוא בדיוק המקרה שבו הוראה נשברת — ונתון שלא סופק לא יכול לדלוף.

**"לא נמצא" ו"אזל" הן תשובות שונות.** מוצר שאינו בגיליון לא אזל, הוא פשוט לא קיים אצלנו. בלי ההפרדה הזו הסוכן יגיד ללקוח שמוצר אזל כשפשוט לא הקלדתם אותו.

**החיפוש עמיד לשגיאות כתיב.** דמיון בייגרמים **ומרחק עריכה**, והגבוה מביניהם. "הקרנה" מול "אקאנה" מקבל 0.25 בבייגרמים ו-0.60 במרחק עריכה — שתי אותיות שונות שוברות בייגרמים. סף 0.58, ומינימום 4 תווים כדי ש"חול" ו"חתול" לא יתנגשו.

**כשהכל אזל, החלופות מדורגות לפי `מתאים ל` ולא לפי מילות החיפוש.** דירוג לפי הטקסט החזיר חמישה מזונות לחתול בוגר למי שביקש מזון לגור, רק כי חלקו מותג.

**תשובה שנגמרת ב"אין" בלי המשך היא תשובה כושלת** גם כשהיא נכונה. תמיד חלופה, בירור, הצעה לעדכן, או טלפון של בעל העסק.

**נפילה למספר הזמנה חושפת מידע.** אם לקוח נותן מספר הזמנה, הסוכן מציג אותה גם אם היא לא שייכת למספר שלו. נוח להדגמה, לא מתאים לפרודקשן. להסרה: מחקו את בלוק ה-`order_number` ב-`lookup_order`.

**היסטוריית השיחה נשמרת לקובץ, וב-Railway מערכת הקבצים נמחקת בכל דפלוי ובכל restart.** בלי ווליום הסוכן זוכר תוך כדי שיחה אבל מתחיל מאפס מול כל לקוח אחרי כל עדכון. `MEMORY_FILE` מצביע ל-`./data`, שהוא `/app/data` בקונטיינר, ולכן זה שתי פקודות בלי לגעת בהגדרות:

```bash
railway volume add -m /app/data
railway redeploy
```

$0.15 ל-GB לחודש לפי שימוש בפועל — קובץ שיחות שוקל קילובייטים. בתמורה: דפלוי כולל רגע קצר של downtime (Railway חוסם שני מופעים על אותו ווליום), ואי אפשר replicas.

**קבוצות מסוננות.** בוט שעונה בתוך קבוצות וואטסאפ הוא הדרך המהירה לחסימת המספר.

## מה לא להבטיח ללקוח

- **Green API הוא חיבור לא רשמי.** מצוין ללמידה ולהדגמה. לעסק שרץ חודשים — WhatsApp Business API הרשמי.
- **AI לא עוקב אחרי הוראות ב-100%.** גם עם הנחיות מצוינות, לפעמים הוא יענה אחרת. לכן נועלים בקוד ולא רק בהוראות.
- **זה לא מחליף בן אדם.** הנחות, תלונות וחריגים חייבים דרך מהירה לבעל העסק.

מי שמוכר את זה כ"פתרון שסוגר הכל" יחזור אחורה. מי שמוכר כ"מוריד 80 אחוז מהשאלות החוזרות" צודק.

## כתיבה לגוגל (לא מופעל)

הסוכן קורא בלבד, ולכן לא צריך הזדהות. כדי שיוכל גם לכתוב — לרשום ליד, לקבוע תור, לעדכן מלאי — אין דרך לעקוף: ה-API של Sheets מחזיר 401 לכל כתיבה בלי הרשאה, גם לקובץ שמשותף לעריכה.

1. **Google Apps Script** — קוד קצר בתוך הגיליון, מפורסם כ-Web App. הסוכן שולח POST עם טוקן משותף. בלי GCP, כמה דקות.
2. **Service Account** — חשבון שירות ב-Google Cloud, קובץ JSON, ושיתוף הגיליון עם כתובת המייל שלו. הדרך הסטנדרטית.

בשני המקרים מוסיפים כלי חדש ב-`src/tools.js` בדיוק כמו הקיימים.
